# Review, dev (uncommitted), 2026-09-09

**Scope**: 24 files, uncommitted working tree (Flutter half of spec 0011 Redis session auth cutover)
**Verdict**: Changes requested

## Summary

This change rips out the JWT access/refresh pair and the `SessionRefresher` retry machinery, replacing it with a single opaque `session_id` credential, a much simpler `SessionTerminator`, and a rewritten `AuthInterceptor` that treats any 401 outside a small allowlist of unauthenticated paths as a dead session. The sweep is thorough and mechanical: `ApiEndpoints.refreshToken`, `StorageKeys.accessToken/refreshToken`, `session_refresher.dart`, and every call site that referenced them are gone, the generated `injection.config.dart` carries no orphaned `SessionRefresher` registration, and the realtime layer (`UserRealtimeOwner`, `SseTransport`, the SSE datasources) was updated symmetrically with no leftover 401-retry branch. New/changed core files (`auth_interceptor`, `session_terminator`, `token_storage`, `sse_transport`, `user_realtime_owner`, `auth_response_model`) have strong, behavior-focused test coverage, including real concurrency tests for `SessionTerminator`'s idempotency. The one real gap is that `AuthRepositoryImpl.login`/`logout` — the exact code path that persists and clears the single AC-19 credential — has zero unit test coverage, and it cannot easily get any because it reaches `FCMTokenManager.instance`, an unmockable static singleton that resolves real `FirebaseMessaging.instance`.

## Major

### 🟠 Credential save/clear path is untestable and untested, `lib/features/auth/data/repositories/auth_repository_impl.dart:31,44,273`
**Problem**: `login()` calls `FCMTokenManager.instance.getToken()` (line 31) and `FCMTokenManager.instance.initialize()` (line 44); `logout()` calls `FCMTokenManager.instance.onLogout()` (line 273). `FCMTokenManager.instance` is `static final FCMTokenManager instance = FCMTokenManager._();` — a singleton constructed with real Firebase-backed defaults (`_defaultReadCredential`, `_defaultUploadToken`, `_defaultDeleteToken`, and `getToken()`'s direct call to `FirebaseMessaging.instance.getToken()`). There is no seam to inject `FCMTokenManager.forTesting(...)` into `AuthRepositoryImpl`, so any unit test that calls `login()` or `logout()` either needs a working Firebase test harness or throws/hangs on the Firebase channel call. As a result, this diff changes `saveTokens(accessToken:, refreshToken:)` → `saveSession(auth.sessionId)` and the logout comment/flow, but no test in this PR (or the existing suite) exercises `AuthRepositoryImpl.login`/`logout` at all.
**Why it matters**: This is precisely the code path spec 0011 AC-19 is about — the app keeping exactly one credential. A future regression here (e.g. someone reintroduces a two-token save, or drops `saveSession` on a refactor, or gets the try/catch around `signOut()` wrong) would not be caught by `flutter test`; it would only surface as users failing to stay logged in or failing to log out, which the guide's coverage bar (Major for security/branching-relevant untested logic) exactly targets.
**Suggested fix**: Give `AuthRepositoryImpl` a constructor seam for the FCM dependency (e.g. accept an `FCMTokenManager`-shaped interface via DI instead of reaching the static `.instance`), so `login`/`logout` can be unit tested with `FCMTokenManager.forTesting(...)` the same way `fcm_token_manager_test.dart` already tests the manager in isolation. This is a pre-existing design wart (not introduced by this diff), but this diff is the moment the credential-handling code inside those methods changed, so it is the right time to close the gap.

## Minor

### 🟡 `SessionTerminator.endSession()` clears whatever credential is currently stored, not the one that failed, `lib/core/network/session_terminator.dart:28-34`
**Problem**: `_endSession()` reads `_tokens.sessionId` and unconditionally calls `_tokens.clear()` — it never checks that the stored session is the same one whose request produced the 401 (or SSE `session_ended`) that triggered the call. A slow in-flight request issued under session A that resolves with 401 *after* the user has logged out and logged back in under session B will still call `endSession()`, which will read session B, clear it, and fire `SessionEvents.notifyExpired()` — logging out a user who just successfully signed in.
**Why it matters**: It's a narrow window (a stale request racing a fast logout+relogin) but the failure mode is a spurious full logout of a session that was never actually revoked, which is the exact kind of "logged out by a race, not because the session died" bug spec 0011 explicitly tries to eliminate versus the old dual-refresh-token design (see spec Positive #3).
**Suggested fix**: Not a regression introduced by this diff — the deleted `SessionRefresher._endSession()` had the identical unconditional-clear pattern, so this is carried over unchanged. Worth a follow-up ticket to have callers pass the session ID that failed (or a monotonically increasing "session epoch", the same pattern `FCMTokenManager._sessionEpoch` already uses for its own retry guard) so `endSession` can no-op if the stored credential has since changed.

## Nits

- ⚪ `lib/core/network/fcm_token_manager.dart:10` — the `CredentialReader` typedef and its default (`_defaultReadCredential`) are well-named post-rename, but the test doubles in `test/core/network/fcm_token_manager_test.dart` still bind a value literally named `'access-token'` to the renamed `readCredential:` parameter; a purely cosmetic leftover from the token→credential rename, harmless but slightly confusing to a future reader.

## Strengths

- The refresh-machinery removal is genuinely complete: no orphaned `SessionRefresher`/`refreshToken`/`accessToken` symbols anywhere in `lib/` or `test/` (verified by grep), and the generated `injection.config.dart` registers `SessionTerminator` cleanly with no dangling `SessionRefresher` provider.
- `SessionTerminator` and `AuthInterceptor` have excellent concurrency and idempotency test coverage (`test/core/network/session_terminator_test.dart`), including the exact "REST 401 + SSE `session_ended` at the same time" scenario that motivated the single-flight `_ending` future.
- `AuthResponseModel` is locked down with a contract test (`auth_response_model_test.dart`) that specifically asserts the old `access_token`/`refresh_token` shape cannot silently reappear, and validates the new 43-char base64url credential format end to end (parse, round-trip, timezone offset preservation).
- The realtime layer's 401/`session_ended` handling in `UserRealtimeOwner` and `SseTransport` is symmetric with the REST interceptor's behavior and is well commented on *why* there is no retry-after-401 branch anymore, matching AC-19 exactly.

## Test coverage

Strong coverage for everything network/session/realtime related that changed in this diff: `auth_interceptor_test.dart`, `session_terminator_test.dart`, `token_storage_test.dart`, `fcm_token_manager_test.dart`, `sse_transport_test.dart`, `user_realtime_owner_test.dart`, and `auth_response_model_test.dart` all assert behavior (not mocks) and cover the interesting edge cases (empty credential, concurrent termination, unauthenticated-path allowlist, contract shape). The one gap is `AuthRepositoryImpl.login`/`logout`, flagged above as Major — it is the only file in scope with credential-handling logic and no test at all, and the reason is a testability defect (`FCMTokenManager.instance` static singleton) rather than an oversight in this PR alone.

## Out of scope / already known

- The Redis-outage-as-permanent-logout behavior (`AuthInterceptor` treats any 401 as a dead session and deletes the credential, so a transient Redis blip logs everyone out) is already known and enrolled as scope item 11 on the backend side — not reported as a new finding here.
